# 候補を確認して採用する

ホームの「確認待ち」または左側メニュー（Androidでは左上メニュー）の「確認待ち」を開きます。

- 確認待ち：プロジェクト案・知識・判断や方針・好みの未承認候補です。
- 要確認：根拠が訂正された候補、破損、同期不足などです。この状態から採用・却下はできません。
- 判断履歴：採用・却下した内容です。承認記録と反映先の両方が届くまで反映済みとは表示しません。

候補を開くと主張、理由、日時、元のメモと訂正履歴、置き換え元を確認できます。「元のメモを開く」では通常の記録画面へ進みます。AI候補は本人が採用するまで正式知識・プロジェクト定義になりません。

## 同じ対象を指すプロジェクト案

名前か別名が一致する案と、4文字以上の名前がもう一方の名前に含まれる案を、本体が1組にまとめます（代表の案と直接重なる案だけで、20件まで）。アプリは代表の1件だけを一覧に並べ、「根拠のメモN件」を添えます。ホームの「確認待ち」の件数、メニューの件数、通知も、1組を1件と数えます。

- 代表の案を開くと、まとめた案の名前・別名・検索語・理由と元のメモも続けて表示します。「N件をまとめて採用する」「N件をまとめて却下する」を押すと、確認画面に代表の案とまとめる案の内容がすべて出ます。依頼には、まとめる案のIDと、確認した時点の内容のhashを添えます（`cover_ids`・`cover_hashes`）。本体は、同じ対象を指す確認待ちの案で、内容が変わっていないことを確かめてから、全部に同じ判断を記録します。
- 採用すると、代表の案の名前・別名・検索語でプロジェクトを作ります。まとめた案の名前は別名に加わりません。必要なら、採用後にプロジェクト画面で別名を足してください。
- 別の取り組みの案が混ざっているときは、その案の「この案にも同じ判断を記録する」のチェックを外すと、この判断から外れます。外した案は確認待ちに残り、後から判断できます。すべて外すと、代表の案だけの判断になります。「この案だけを判断する」から、まとめた案の1件だけを採用・却下することもできます。
- 採用を依頼した案が反映されるまでは、その案と名前か別名が同じ案を含むまとめた判断は依頼できません。採用でプロジェクトができると、名前か別名が同じ案は古い案として「要確認」へ移り、その案を含むまとめた依頼の全体を本体が受け付けられなくなるためです。画面に、名前か別名が同じ案の名前を示します。同期して残った案を確かめてから判断するか、示された案のチェックを外して判断してください。名前も別名も違う案だけなら、まとめて判断できます。却下の依頼は、ほかの案の判断を妨げません。「反映されるまで」は、Miniが作り直した確認待ちの一覧がこの端末に届くまでです（採用の記録だけが先に届いている間も、止めたままにします）。
- 反対に、まとめた判断を依頼してから反映されるまでは、その判断に含めた案と名前か別名が同じ案の採用は依頼できません。本体は1回の実行に届いた依頼をIDの順に受け付けるので、後から依頼した採用が先に反映されることがあり、そのときはまとめた依頼の全体が受け付けられなくなるためです。却下はできます（まとめた採用が先に反映されて、その案が古い案になったときは、その却下だけが受け付けられません）。
- 止めるのは、この端末に同期済みの採用・却下の依頼との組み合わせだけです。ほかの端末がまだ同期していない依頼や、名前か別名が同じプロジェクトの新規作成・別名の変更が先に反映されたときは、まとめた依頼が受け付けられないことがあります。そのときは、下の「受け付けられなかったとき」のとおり、もう一度判断できます。
- まとめるのは、この端末で確認待ちとして読めている案だけです。根拠が未同期の案や、判断を依頼済みの案（その案だけの依頼も、ほかの案とまとめた依頼も）は、1件ずつ並びます。1回の判断でまとめられるのは20件までです。
- まとめて判断された案は、判断履歴に「「代表の案の名前」とまとめて判断」と表示します。
- まとめは、対応した本体が一覧に付ける印に従います。対応前の本体では、これまでどおり1件ずつ並びます。対応前のアプリは、まとめた案を1件ずつ表示し、1件ずつ判断します。

## 採用・却下の操作

「採用する」「却下する」を押すと確認画面が開きます。内容を確認し「採用を依頼」「却下を依頼」を押してください。保留は「保留して閉じる」、確認の取消は「取消」です。どちらも依頼を保存しません。

依頼はこの端末の `Input/REQ-….md` に新しく保存します。同期後にMiniが最新状態を再検証します。「依頼保存済み・Miniの判断待ち」と「承認済み・反映済み」は別の状態です。受付状況と判断履歴を再読込して確認してください。別端末で同じ判断をしても正式データは増えず、反対の判断は先に確定した記録が優先されます。

Miniが依頼を受け付けられなかったとき（確認した後に候補や採用先が変わっていた、まとめた案の1件が先に判断されていた、など）は、候補に「前の依頼は受け付けられませんでした」と表示し、確認待ちの件数にも戻します。まとめた案の依頼が受け付けられなかったときは、代表の案の行と、その案の欄にも示します。受付状況には受け付けられなかった依頼として並びます。プロジェクト案の採用・却下では、本体は詳しい理由を記録しません（知識・方針の採用で、採用先のプロジェクトが統合済みだったときは、受付状況に理由が出ます）。内容を確かめて、もう一度判断を依頼できます（新しい依頼として保存します）。候補の詳細を開いたままでも、保存した依頼が受け付けられなかったことが同期されると、もう一度判断できる表示に戻ります。本体は受け付けられなかった依頼を実行のたびに確かめ直すので、状況が変わると前の依頼が受け付けられることがあります。そのときも記録される判断は1つで、先に記録された判断が残り、後から届いた反対の判断は受け付けられません。

保存結果が不明な場合は再送せず、受付状況の保存確認を使います。確認中に同期内容やVaultが変わると操作を止め、再確認を求めます。候補の本文が同じでも元メモに新しい訂正があれば、Miniでの再整理を待ちます。既存REQや候補、承認記録を直接編集しないでください。

この機能には候補一覧を生成できる本体とQuickAddの対応版が必要です。本体の `dashboard` または `cycle` が `90_system/review/index.json` と必要な分割pageを更新します。一覧が未同期なら同期とMini側の更新を確認してください。ObsidianのHOMEとQuickAddも同じ一覧・判断記録を使います。

アプリ専用サンプルは初回作成後に上書きしません。以前の版で作ったサンプルには新しい候補が追加されないため、候補の確認には対応本体で作成した架空Vaultを選択してください。実Vaultの初期化やアプリデータの削除で代用しないでください。
